# Pintos 우선순위 구현 비교와 통합 결과

2026-10-13에 제공된 세 ZIP의 코드를 직접 비교하고, 같은 Ubuntu 22.04 x86_64 개발 컨테이너에서 GCC로 빌드해 QEMU로 실행했다. 평가는 알람과 우선순위 스케줄링 범위다.

## 추천: 상민 → 선우 → 형광

상민을 통합의 기반으로 추천한다. 상민과 선우는 제공된 기본 테스트에서 동점이지만, 상민은 추가 검증에서 더 많이 통과했고 알람으로 깨어난 높은 우선순위 스레드를 바로 실행하도록 처리한다. 기본 우선순위 `priority`와 실제 실행 우선순위 `eff_priority`의 의미도 일관돼 통합하기 좋다. 다만 상민 원본에도 아래 결함이 있어 그대로 제출하는 것보다 통합본을 사용하는 편이 낫다.

| 구현 | 기본 알람·우선순위 테스트 | 추가 동작 검증 | 합계 |
|---|---:|---:|---:|
| 상민 | 18/18 | 4/9 | 22/27 |
| 선우 | 18/18 | 3/9 | 21/27 |
| 형광 | 15/18 | 3/9 | 18/27 |
| **통합본** | **18/18** | **9/9** | **27/27** |

추가 검증은 이번 비교를 위해 작성한 테스트이며 공식 채점 점수는 아니다. 이 통과 수는 테스트한 상황에 대한 결과이고, 모든 가능한 상황에 대한 정확성이나 성능의 증명은 아니다.

## 원본에서 확인한 문제

형광의 기본 테스트 실패는 `priority-donate-one`, `priority-donate-sema`, `priority-donate-chain` 세 개다. 락 해제 시 같은 락의 기부자를 하나만 제거하고, 세마포어 대기자의 우선순위가 기부로 바뀌어도 깨우기 전에 재정렬하지 않는다. 중첩 기부도 락 소유자와 그 위 소유자까지만 갱신해 긴 연결을 처리하지 못한다.

상민은 준비 상태인 락 소유자에게 기부가 들어와도 준비 큐를 재정렬하지 않는다. 조건변수는 처음 대기할 때의 순서로 깨워서 이후 기부를 반영하지 못한다. `sema_up()`은 인터럽트에서도 직접 `thread_yield()`를 호출한다.

선우는 세마포어와 조건변수를 깨우기 전에 재정렬하고 중첩 기부를 최대 8단계 전달한다. 그러나 준비 큐의 기부 변화는 반영하지 않고, 알람으로 깨어난 높은 우선순위 스레드의 즉시 선점을 요청하지 않는다. 조건변수 비교 함수가 내부 세마포어의 첫 대기자를 읽어서, 아직 `sema_down()`에 들어가지 않은 대기자가 있으면 잘못된 메모리를 스레드로 해석한다. 선점 함수도 인터럽트 문맥을 구분하지 않는다.

세 원본 모두 락 인계 뒤 남은 대기자의 기부를 새 소유자에게 연결하는 상황과, 깨어난 대기자가 다른 스레드의 락 재획득 때문에 다시 기다리는 상황을 통과하지 못했다.

## 어떤 부분을 합쳤는가

- **상민:** 프로젝트 기반, 기본·실제 우선순위의 분리, 정렬된 알람 대기열과 알람 선점, 기부자 목록 전체 순회, 세마포어 해제 시 재정렬.
- **선우:** 최대 8단계의 중첩 기부 전달, 공통 선점 함수의 구조, 조건변수를 신호 시점의 우선순위로 재평가하는 방식.
- **형광:** 기부로 준비 상태 스레드의 우선순위가 바뀌면 준비 큐를 다시 정렬하는 방식, 락과 기부 정보를 인터럽트가 끼어들지 않는 구간에서 갱신하는 방식.
- **추가 수정:** 인터럽트에서는 복귀 시 선점 요청, 일반 문맥에서는 필요한 경우에만 양보. 기본 우선순위 변경 후 모든 기부를 반영해 실제 우선순위를 재계산. 해제한 락의 기부자를 모두 제거. 락을 얻은 새 소유자에게 남은 대기자의 기부를 연결하고, 락을 다시 기다리게 되면 기부도 재시도. 조건변수 대기자에 스레드 포인터를 저장해 비어 있는 내부 대기열을 읽지 않도록 처리.

[KAIST Pintos 우선순위 명세](https://casys-kaist.github.io/pintos-kaist/project1/priority_scheduling.html)에 따라 락의 다중·중첩 기부와 우선순위에 따른 깨우기를 처리했다. 중첩 기부의 제한은 명세가 허용하는 8단계다.

## 변경 파일과 결과물

이 저장소의 루트에 통합 프로젝트를 반영했다. 상민 원본과 비교해 실행 코드를 수정한 파일은 다음 네 개다.

- `pintos/threads/thread.c`
- `pintos/threads/synch.c`
- `pintos/include/threads/thread.h`
- `pintos/include/threads/synch.h`

`merged-vs-sangmin.patch`에는 이 네 파일의 변경이 담겨 있다. 기존 공통 타이머 구현은 그대로 사용하며, 일반 리스트 라이브러리에 별도 함수를 추가하지 않았다. 통합 프로젝트에 `README-MERGE.md`와 `run-priority-tests.sh`를 추가했다.

기존 `dev` 브랜치의 기록 위에 새 커밋으로 반영했다. 기존 개발 환경 설정과 현재 열려 있던 로컬 프로젝트의 진행 중인 수정은 유지했다.

## 다시 실행하기

Linux Pintos 개발 컨테이너에서 통합 프로젝트의 기본 18개 테스트는 다음처럼 실행한다.

```sh
./run-priority-tests.sh
```

추가 9개 검증은 프로젝트를 임시 복사한 다음 설치한다. 아래 명령은 이 저장소의 루트에서 실행한다.

```sh
pintos_regression_copy=$(mktemp -d /tmp/pintos-regression.XXXXXX)
git archive HEAD | tar -x -C "$pintos_regression_copy"
pintos_regression_tests=$(python3 priority-review/install-regressions.py "$pintos_regression_copy")
export PATH="$pintos_regression_copy/pintos/utils:$PATH"
cd "$pintos_regression_copy/pintos/threads"
make
make -C build check TESTS="$pintos_regression_tests"
```

추가 검증 설치기는 임시 복사본의 테스트 목록과 타이머에 검증용 호출 지점을 추가한다. 배포한 통합 소스에는 이 호출 지점이나 추가 테스트가 들어 있지 않다. 인터럽트 중 `sema_up()` 호출을 실제 QEMU 커널에서 확인하기 위한 장치다.

함께 제공된 `SW-AI-W07-PintOS-priority-merged.zip`의 `priority-review/evidence/<구현>/baseline/`과 `priority-review/evidence/<구현>/regressions/`에 개별 테스트의 출력, 오류, 판정 및 빌드·실행 로그가 있다. 이 저장소에는 비교 보고서, 판정 요약, 추가 검증 소스와 설치기를 반영했다. `validation.json`에는 판정 목록, 입력 ZIP의 SHA-256, 통합 핵심 소스의 SHA-256이 있다. 기존 Pintos 공통 코드에서 발생하는 컴파일 경고는 남아 있으며, 통합한 두 C 파일에서 새 경고는 확인되지 않았다.

## 범위와 제한

**MLFQS는 세 압축파일 모두 미구현이라 이번 통합 범위에 포함하지 않았다.** `nice`, `recent_cpu`, `load_avg` 및 동적 우선순위 계산은 아직 구현해야 한다. 이 기능은 [별도의 고급 스케줄러 과제](https://casys-kaist.github.io/pintos-kaist/project1/advanced_scheduler.html)다.

일반 `make check`는 MLFQS 테스트 9개까지 포함한다. 따라서 여기서 말하는 **27개 통과는 기본 알람·우선순위 18개와 이번 추가 검증 9개**를 뜻하며, MLFQS를 포함한 전체 과제 통과를 뜻하지 않는다. User Programs, VM, Filesystem 과제도 이번에 구현하거나 검증하지 않았다.
